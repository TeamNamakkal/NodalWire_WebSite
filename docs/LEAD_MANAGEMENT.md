# Lead Management — Module Documentation

Internal business-development tool. Visible only to approvers (`role === 'admin'`
or `isTimeApprover === true` on the employee record) — currently Surendran and
Julius. Lives inside the authenticated portal (`portal.html`), not on the
public site.

## Storage

SQLite, via Node's built-in `node:sqlite` (no new npm dependency; requires
Node 22.5+, confirmed working on Node 22.23 both locally and on the
production EC2 host). Database file: `data/leads.db` (gitignored — contains
real business data, provisioned directly on the server the same way
`employees.json` is).

All queries live in `scripts/lib/leads-db.mjs`. If this ever needs to move to
Postgres or another database, only that file should need to change.

Tables:
- `leads` — one row per lead. Key fields: `lead_number` (public-facing ID,
  distinct from the internal `id` autoincrement row ID), `status`,
  `priority`, `owner_id`/`owner_name`, `next_followup_at`, plus full audit
  trail (`created_at`/`created_by`, `updated_at`/`updated_by`).
- `lead_activities` — append-only, immutable. Every status change, note, edit,
  and follow-up date change becomes its own row here. The lead's own record
  is never used to store free-text history — the UI always reads the
  timeline from this table.

## Lead ID generation

Format: `NW-LD-0001`, `NW-LD-0002`, ... Generated by scanning the highest
existing `lead_number` and incrementing (`generateLeadNumber()` in
`leads-db.mjs`). Never derived from the SQLite row ID.

## Lead statuses & service categories (centralized)

Defined once in `scripts/lib/leads-db.mjs` as `LEAD_STATUSES`,
`LEAD_PRIORITIES`, and `SERVICE_CATEGORIES` — exposed to the frontend via
`GET /api/leads/meta` rather than hardcoded in the UI, so they can be
changed in one place.

- Statuses: Initiated, Contacted, Discussion, Proposal, Negotiation, Won,
  Lost, On Hold.
- Priorities: Low, Normal, High, Critical.
- Service categories: Optical Networks, FTTH / PON, Wi-Fi, Microwave, Remote
  Property Connectivity, Data Center / Networking, Private Networks,
  Engineering Labs, GIS / Network Planning, Other.

## Activity history

Every meaningful change creates a separate `lead_activities` row — never an
overwrite. Activity types: `lead_created`, `note_added`, `status_changed`,
`followup_changed`, `lead_edited`, `ai_draft_generated`, `email_marked_sent`.

## API endpoints

All routes are handled in `scripts/lib/leads-routes.mjs`, delegated to from
`scripts/serve.mjs` for any request starting with `/api/leads`. All require
`requesterId` and enforce approver-only access server-side.

- `GET /api/leads/meta` — statuses, priorities, service categories
- `GET /api/leads/followups` — `{overdue, dueToday, upcoming}`
- `GET /api/leads/analytics` — `{byStatus, byMonth, byService}`
- `GET /api/leads` — full lead list
- `POST /api/leads` — create a lead (auto-generates ID, sets status
  `Initiated`, logs `lead_created`, sends the new-lead notification email)
- `GET /api/leads/:leadNumber` — lead detail + full activity timeline
- `PUT /api/leads/:leadNumber` — edit lead fields (each changed field logs a
  `lead_edited` activity)
- `POST /api/leads/:leadNumber/update` — bundled status / follow-up date /
  note update from the Lead Detail action area; each provided change is
  logged as its own activity
- `POST /api/leads/:leadNumber/ai/:draftType` — AI email draft
  (`draftType` is `introduction` or `followup`); returns
  `{configured: false}` until a provider is wired up
- `POST /api/leads/:leadNumber/email-sent` — future "Mark as Sent" action,
  logs `email_marked_sent`

## Environment variables

```
LEAD_NOTIFICATION_EMAILS=you@nodalwire.com,julius@nodalwire.com
AI_PROVIDER=none            # openai | anthropic | gemini | none
OPENAI_API_KEY=
ANTHROPIC_API_KEY=
GEMINI_API_KEY=
```

Uses the existing SMTP settings (`SMTP_HOST`/`PORT`/`USER`/`PASS`/`FROM`)
already configured for password-reset email. A new-lead notification
silently skips (does not fail lead creation) if `LEAD_NOTIFICATION_EMAILS`
is unset or SMTP isn't configured.

## AI provider extension point

`scripts/lib/ai-provider.mjs` exports `generateLeadEmail(draftType, context)`.
No provider is implemented in V1 — `AI_PROVIDER` defaults to `none`, so the
function always returns `{configured: false, message: 'AI integration not
configured.'}`, and the UI shows that message instead of a draft box.

To add a real provider later: implement that provider's `generate()` method
in `PROVIDERS` (openai/anthropic/gemini), set `AI_PROVIDER` and its API key
in `.env`. No changes needed to `leads-routes.mjs` or `js/leads.js` — both
already handle both the "not configured" and real-draft response shapes.

## Frontend

`js/leads.js` — single self-contained module (matches the pattern used by
`js/employees.js`, `js/timebooking.js`, etc.), registered into the portal
sidebar via `window.NWPortal.register('Lead Management', renderInto,
{ approverOnly: true })`. No client-side routing exists anywhere in this
app (see main `docs/PROJECT_STRUCTURE.md`) — Lead Detail is an in-module
view swap, not a real URL, consistent with every other portal section.

Charts (status donut, monthly bar, service-mix horizontal bar) are hand-rolled
inline SVG — no charting library, consistent with the portal loading zero
external CDN dependencies.

## Known V1 limitations (by design, not oversights)

- No deep-linkable lead URLs (`/admin/leads/NW-LD-0001`) — the whole portal
  has no router; this would be a larger change than this feature warrants.
- AI Assistant has no real provider wired up.
- "Opportunity Intelligence" (future market-signal detection feature) is not
  implemented — deliberately out of scope for V1.
